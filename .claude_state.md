## RESOLVED 2026-09-20: Send_Task cadence conflict (100 vs 200 vs 80 Hz)

**It was never a contradiction. The cadence is mode-dependent.** Confirmed from
source and then measured on the running drone via the firmware DWT profiler.

| Mode | Call site | Pacing | Cadence |
| --- | --- | --- | --- |
| Normal flight (`id_frame_on`=0 AND `of_frame_on`=0) | `USER/main.c:340` `vTaskDelayUntil(&PreviousWakeTime, pdMS_TO_TICKS(10))` | **absolute** | **100 Hz, stable** |
| SysID/OF high-rate (`id_frame_on` OR `of_frame_on`) | `USER/main.c:305` `vTaskDelay(pdMS_TO_TICKS(5))` | **relative** | ~200 Hz *nominal ceiling*, always slower |
| MIXED (measured) | `TASK/send_data.c:476` | relative 5 ms + DMA busy-wait | 80.2 Hz (12.47 ms) |

The 80.2 Hz is the same branch as the 200 Hz one. Because `vTaskDelay` is
RELATIVE, the real period is 5 ms + body execution time; the legacy UART5 DMA
busy-wait adds ~3.7-8.5 ms (`send_data.c:836`), giving ~12.47 ms = 80.2 Hz.
That arithmetic closes the gap between all three numbers exactly.
`main.c:269-277` documents why this branch MUST NOT use `vTaskDelayUntil`:
absolute pacing there "RUNS AWAY" to ~270 Hz and saturates the UART.

### Live hardware measurement (drone powered, 2026-09-20)

```
g_send_prof.initialized      1
g_send_prof.period_cycles    1680001
g_send_prof.period_cycles_min 1665339
g_send_prof.period_cycles_max 1688170
SystemCoreClock              168000000
mrac_flags.id_frame_on       0
mrac_flags.of_frame_on       0
g_telemetry_mode             1
```

168e6 / 1680001 = **99.99994 Hz** (10.000006 ms). Jitter band 99.52-100.88 Hz
(from max/min cycles). Both mode flags clear => normal-flight branch
(`main.c:340`), and the measurement lands within 6 ns of the nominal 10 ms
tick, which is what absolute pacing is supposed to look like.

### Consequence for the code

- `firmware_contract.py:103` `SUBSCRIBE_SEND_TASK_HZ = 100` is **correct** for
  normal / SUBSCRIBE_ONLY mode. Leave it.
- `manifest_layer.py` `200 // divider` is correct **only** in the id/of-frame
  branch, and even there 200 is a ceiling never actually reached.
- `boot_default_layout.py:189` 80 Hz is real measured MIXED-mode behaviour.
- `rate_planner.py` making `cadence_hz` a parameter (default
  `SUBSCRIBE_SEND_TASK_HZ`) is **vindicated** - there is no single right value.
- Firmware itself instructs the host (`send_data.c:479-480`): "the host must
  measure actual Hz from arrival times rather than assume 80.2/divider."

Bisected against a clean temp dir: copying `.claude/`, `AGENTS.md` and running
`git init` all still answer `READY`. So it is not settings, not the project
instructions, not trust (`~/.claude.json` already has

It is git. Claude Code refreshes the index at startup, and in this repo from WSL
that never finishes:

```
git status --porcelain            secs=240  (timeout, incomplete)
git status --porcelain -uno       secs=201  (timeout, incomplete)
git ls-files -o --exclude-standard secs=29  files=183
git diff --quiet -- API           secs=120  (timeout)
tracked files: 866   tracked OBJ/ files: 310   OBJ bytes: 111,421,493
```

The untracked walk is cheap; the *tracked* half is what stalls, and even a
single-directory `git diff -- API` stalls, because any index refresh re-hashes
every file whose stat data does not match — which is all 310 dirty `OBJ/` files,
111 MB, over the 9p `/mnt/c` mount. Windows-side git and WSL git record
different `st_dev`/`st_ino`, so each side invalidates the other's stat cache and
the 111 MB re-hash repeats on every single command.

**Fix applied** (repo-local, reversible, `git config --local`):

```
core.checkStat    minimal     # compare size+mtime only, ignore ino/dev/ctime
core.trustctime   false
core.preloadIndex true
```

`core.checkStat minimal` is the documented remedy for sharing a working tree
between two git builds. With it set, one uninterrupted `git update-index
--refresh` from WSL should warm the index for both sides.

**What this invalidates:** the two ark worker waves earlier in this session were
recorded as dying on provider quota. They were not. They were hanging on git
startup and being killed by the wrapper timeout. Any past conclusion of the form
"ark is out of quota" that rests only on an empty worker log is unsafe.
