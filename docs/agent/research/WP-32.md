# WP-32 research: what mature flight-stack pipelines do that we do not (2026-10-04)

## Question
Compare this repo's firmware, ground station and dashboard against PX4, ArduPilot, Betaflight, embedded practice and GCS/data
tools (QGC, Mission Planner, Foxglove, PlotJuggler); rank the gaps to close first.

## Answer (bottom line)
Our safety logic is real (in-flight supervisor `API/wfb_safety.c`, host-side `campaign_preflight`, a fail-closed ARM gate in the
dashboard), but it is spread across three places. Two things mature stacks always have are thin here: (a) a gate that runs on every commit
(host tests, static analysis, a non-Keil compile, SITL), and (b) firmware-side checks that refuse to arm and say why. Order to close:
1. One check gate per commit + CI (P1). 2. Firmware pre-arm checks with reason codes (F1). 3. A LAND/ABORT action and status strip
on every dashboard workspace (D1). 4. Watchdog + reset cause (F2). 5. SIL + fault injection in the gate (P2, on top of WP-31).
6. Self-describing session logs with a tunables snapshot and build id (P3). 7. Alert levels + spoken warnings (D2, D3).
Remaining items (budgets in telemetry, tunable metadata, full-rate capture, flight review) come after these.

## Firmware: top 5 and package outline
1. **F1 pre-arm checks (#2).** `API/prearm.c/.h`: `PREARM_ROW` table (check id, threshold, unit, enabled) per the table pattern; checks:
   estimator ready, battery V at rest, RC link, |roll|,|pitch| on pad, no latched `wfb_safety` trip, task fps from `system_monitor`.
   `FlightFSM` arms only if mask == 0; export `g_prearm_fail_mask` (uint16) + first-fail id. Test `tests/firmware_host/test_prearm.c`
   (each check alone, mask bits, RC and GS paths). Done: host test green, EQUIV OK, mask visible in livewatch. Changes flight
   behaviour (can refuse arm): needs operator approval and a bench session before flight.
2. **F2 watchdog (#4).** IWDG refreshed only from `SystemErrorDetect` when every critical task counter moved this period
   (counters exist, `TASK/systemmonitor_task.c:10`). Timeout from a measured worst loop time, not a guess. Boot: copy RCC_CSR to
   `g_reset_cause`, clear flags, stream once. Test: host test of the check-in logic; bench: hang a task, see reset + cause. Behaviour change.
3. **F3 budgets (#9).** 1 Hz telemetry var (default off): min stack HWM over tasks + task index, CPU% of stabilizer, max loop us.
   `docs/firmware-quality.md` budget table (WP-36 B). Done: values match `python -m ground_station.livewatch` RTOS view.
4. **F4 tunable metadata (#10).** Comment tags beside each `*_ROW` column (`@unit @min @max`), host script -> `generated/params.json`,
   pytest cross-checks it against `capability_manifest.json`. No behaviour change.
5. **F5 static analysis (#14).** Checked-in `.clang-tidy`; cppcheck (+ misra addon, report-only) on `API/`; host builds `-Wall -Wextra -Werror`.

## Ground station + pipeline: top 5 and package outline
1. **P1 one gate (#1).** `tools/check.sh` = all `tests/firmware_host` + `API/tests` C tests through one runner, scoped pytest,
   `run_mrac_equiv.py`, clang-tidy, `arm-none-eabi-gcc -fsyntax-only` (skip with message if absent; not on this PATH), SIL smoke.
   Same script in `.git/hooks/pre-commit` (opt-in installer) and `.github/workflows/check.yml`. Done: exit 0 locally, red on a
   planted failing test. A full GCC link needs a GNU startup file + linker script (Keil startup is armasm syntax: UNVERIFIED here).
2. **P2 SIL + fault injection (#5).** On WP-31's SIL: scenarios link loss, low V, tilt, fence; assert the `wfb_safety` trip and
   action. Done: scenario matrix in the gate under 2 min.
3. **P3 self-describing session (#6).** At session start write build id/git, contract versions (`firmware_contract.py:38-45`),
   full tunables snapshot, var list with type/unit/rate; log each param command as an event. Export to MCAP (S31) or ULog-like.
   Test: round-trip a session, schema and params read back.
4. **P4 full-rate capture window (#11).** Short high-rate capture over the probe stream (livewatch) for replay windows; measure
   radio throughput first. Cost L; after P3.
5. **P5 flight review (#13, #12).** `analysis/flight_review.py` -> HTML per ledger row: setpoint vs actual, FFT, motor
   saturation, sample-interval histogram. Pairs with WP-34 replay.

## Dashboard UX (one-operator lab): top 5 and package outline

## Alternatives considered
- Port PX4 or ArduPilot whole: rewrites the FreeRTOS/Keil stack under active MRAC campaigns; we copy practices only.
- MAVLink + QGC as GCS: QGC lacks our MRAC/campaign panels; possible later bridge for Fly-view-style safety only.
- Onboard SD blackbox like Betaflight (S18): no SD/flash logger found in API/TASK/USER/BSP; hardware question, so P4 uses the probe.
- Full MISRA compliance: too costly for a research airframe; an advisory subset via cppcheck/clang-tidy is enough.
