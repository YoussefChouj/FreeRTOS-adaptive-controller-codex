# WP-25 research: automatic PID tuning for the indoor quadrotor (2026-10-03)

## Question
Which automatic PID tuning method should we implement for this indoor quadrotor (STM32F4 + FreeRTOS, cascaded
angle -> rate PID, MRAC on top, 1.3 x 1.7 x 1.4 m soft fence, scripted GS flights, operator on RC), and how exactly?

## Platform facts checked in the repo
- `API/pid.c:23-24`: roll/pitch rate rows Kp 5, Ki 0.01, Kd 10; angle rows Kp 3.0, Ki 0.02, Kd 8 (`PID_ROW`).
- `API/pid.c:118-125`: discrete gains: `SumE += E` per tick, `Ud = Kd*(E-PreE)`. So Ki_fw = Ki_cont*dt and
  Kd_fw = Kd_cont/dt with dt = 0.005 s; D acts on error, no D filter in this function.
- `API/sysid.h`: an excitation module already exists: chirp or 20-tone multisine added to ONE axis's rate
  setpoint, outer angle loop bypassed on that axis, 200 Hz, cosine ramp 1.5 s, abort on |angle| > 30 deg,
  XY soft 50 cm, alt 0.30-1.50 m, RC dead-man; it logs the dither as an instrument for an IV estimate
  G = Phi_xd/Phi_ud. `USER/main.c:283-296`: a 200 Hz ID frame streams during SysID.
- `ground_station/research/sim/cascade.py:432` `fit_rate_plant`: fits d(rate)/dt = k*lag(delay(U)) (integrator +
  first-order lag + delay) by grid over delay and tau. `API/mrac.h:280` `output_injection_on` gates MRAC output.

## Answer (recommendation)
**Model-based tuning from frequency-domain identification, offline on the ground station**: excite the rate
loop with the existing multisine/chirp, estimate the plant FRF (IV), fit integrator+lag+delay, compute PID gains
against margin specs, verify in flight with auto-revert. Rate loop first, then angle loop. Optional last
stage: safe Bayesian refinement of 1-2 scale factors over a few scored flights. It is the PX4 idea
(identify, then compute gains from a model) with the identification done offline, which we already have.

Why here: no large manoeuvres (ArduPilot twitches 20 deg at up to 180 deg/s and needs a large open area);
no deliberate limit cycle (relay); the MCU only runs the existing excitation FSM (no RLS, no design math in
firmware); the GS can show the fit and the proposed gains to the operator before they are applied.

### Algorithm (proposed values; none measured on this airframe yet)
1. Pre-flight: MRAC `output_injection_on = 0` for all tuning flights; record the current PID rows as `G_prev`.
2. Rate-loop ID, roll then pitch (yaw last, optional). Hover at 0.5 m under position hold. `SysID_Start(axis,
   MULTISINE, f0 = 0.5 Hz, f1 = 15 Hz, amp, 20 s)`. Amplitude: cap the angle swing at 5 deg, so
   amp(f) = min(60 deg/s, 2*pi*f*5 deg) (the existing pre-emphasis already shapes energy by frequency).
   Two repeats per axis. Tighten the tuning abort to |angle| > 15 deg (sysid default is 30).
3. GS identification: IV FRF G(jw) = Phi_xd/Phi_ud on the 200 Hz ID frame; keep bins with coherence >= 0.6
   (our threshold). Fit G(s) = k*e^(-sT)/(s(tau*s+1)) by weighted least squares on the complex FRF (reuse the
   `fit_rate_plant` model; start the fit from its time-domain result). Reject if fit residual is large or
   coherence holds over less than half the band.
4. GS rate-PID design on the discretised fitted model (dt 0.005 s, include the fitted delay T):
   choose continuous Kp, Ki, Kd that minimise simulated step ITAE subject to phase margin >= 45 deg,
   gain margin >= 6 dB, max |S| <= 2 (6 dB), and no clamp saturation (UMax, UpMax, UdMax rows) for a 30 deg/s
   step. PX4 equivalent target for a sanity check: rate rise time 0.14 s at damping 0.7. Convert to firmware
   units (Ki_fw = Ki*0.005, Kd_fw = Kd/0.005).
5. Step limit: each gain in [0.7, 1.3] x `G_prev` per iteration (ArduPilot moves 5% per twitch; we move per
   flight, so a larger bounded step). If the design wants more, take the clamp and iterate.
6. Verification flight with the candidate: hover 20 s + rate doublets +-30 deg/s on the tuned axis, re-run a
   short low-amplitude multisine to re-measure the loop margins. Firmware auto-reverts to `G_prev` on: sysid
   abort, RC stick > 5% (PX4 uses 0.05), any WFB safety trip, or gyro RMS in 15-60 Hz > 2x baseline for 0.5 s.
7. Angle loop next, on the accepted rate gains: inject the excitation at the angle setpoint (Betaflight
   PR 15196 approach), amp 3 deg, 0.3-5 Hz, 20 s. Plant = closed rate loop / s. Pick angle Kp for an angle
   crossover about 1/4 of the rate crossover, PM >= 50 deg; keep angle Ki/Kd at current values unless the fit
   needs them. Verify with +-5 deg angle doublets.
8. Optional refinement: SafeOpt-style safe BO over (rate gain scale s_r, angle Kp scale s_a) in [0.8, 1.2],
   cost = hover angle RMS + doublet ITAE, safety = score above the baseline flight's score. Stop after 8
   flights or no improvement in 3.

### Split
- Firmware: existing `sysid.c` FSM + excitation (new: angle-setpoint injection point, tighter 15 deg abort);
  gain row set via existing `set_params`; new: `G_prev` snapshot + revert, the gyro-band oscillation watchdog.
- Ground station: campaign script, IV FRF, fit, PID design, scoring, gain proposal shown for operator Go.

## Workflow-B campaign mapping (about 6 flights + up to 8 optional)
| # | Flight | Logged | Pass |
|---|---|---|---|
| F0 | Baseline hover 30 s, current gains | att, rate Des/FB/U, pos | no abort; gives baseline score |
| F1 | Roll rate multisine x2 (~55 s airborne) | 200 Hz ID frame: dither, rate sp, gyro, U | coherence >= 0.6 over >= half band; no abort |
| F2 | Pitch rate multisine x2 | same | same |
| F3 | Candidate rate gains: hover + doublets + short ID | as F0 + ID frame | no revert; PM >= 45 deg re-measured; overshoot <= 20%; hover RMS <= baseline*1.1 |
| F4 | Angle-setpoint multisine roll+pitch | ID frame + angle | coherence as F1 |
| F5 | Final gains: hover 30 s + angle doublets | as F0 | as F3; operator accepts, else rows revert at disarm |
| F6+ | Optional safe-BO flights | as F5 | safety score >= baseline |
Each flight stays well inside the 120 s airborne cap; a failed pass repeats that flight once, then stops.

## Alternatives considered
- PX4 online ARX/RLS + GMVC in firmware: proven, about 40 s, but puts RLS and design math on the MCU and applies
  gains with no human look; we already stream 200 Hz ID data and have an IV pipeline, so do it on the GS. Keep
  its specs (rise time 0.14 s, damping 0.7, 0.05 stick abort) as sanity checks.
- ArduPilot twitch AutoTune: 180 deg/s twitches, 20 deg leans, minutes per axis, large open area. Does not fit
  a 1.3 m fence.
- Relay (Astrom-Hagglund) / Ziegler-Nichols: drives a sustained oscillation at the -180 deg point, one
  frequency only, 5-20% Ku error; unsafe and imprecise for an airborne vehicle indoors.
- Betaflight: chirp + offline analysis is the same family as our recommendation (supports it); its in-firmware
  "autotune" was found only in blogs, not checked in primary sources.
- Pure Bayesian optimisation / IFT / extremum seeking from scratch: needs many flights per parameter set;
  only worth it as a low-dimensional refinement after the model-based step (step 8).

## Unknowns
- Plant bandwidth, delay and coherence on this airframe: the 0.5-15 Hz band, 60 deg/s cap, 0.6 coherence and
  15 deg abort are proposals to check on F1, not measured values.
- Whether 115200-baud 200 Hz telemetry gives enough coherence above ~10 Hz (sysid.h notes a ~200 Hz cap).
- The PX4 step period and exact ARX orders were not read; the SafeOpt PDF text was not extractable, so flight
  counts for BO are our guess.
- Effect of the D term without a filter (`pid.c:125`) on higher designed Kd; may need a D low-pass first.
- How the MRAC re-tunes on top of new gains; re-check MRAC with `output_injection_on = 1` after acceptance.
