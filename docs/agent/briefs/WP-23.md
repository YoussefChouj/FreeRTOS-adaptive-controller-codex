## Why
The first live workflow-B launch (2026-10-03, hover_ladder, pack P4000-1) failed at preflight and the agent needed
many ad-hoc commands to find out why. The operator's goal: workflow B is the long-term tool for collecting
experiment data across many controllers and variants. The agent must launch it in the minimal number of
deterministic steps; the operator only answers questions, says go, and keeps hands on the RC sticks.
Already fixed (do not redo): Go is the operator's arm consent; `allow_agent_arm` is no longer a campaign gate
(`campaign_api.arm_allowed`, commit 90e1c83) and the panel checkbox is gone (13341ca).

Problems seen live, all must be handled:
1. `get_state` showed `arm_state` "armed" with the drone on the pad, before any arming. Find where `arm_state`
   is derived (service/agent/view-model code) and whether it can misreport (stale value, wrong field, default).
   Fix it or make preflight report the raw source field next to it.
2. The panel's `window.confirm` was blocked by the operator's browser, so the action silently did nothing.
   Grep `window.confirm` in `docs/dashboard-platform/shell/plugins/*.js`: replace every one on a workflow-B
   path (campaign, approval queue, command panel, path panel) with an in-panel two-click confirm (button turns
   "Confirm <action>?" for 5 s), and make every failed action show its error in the panel.
3. Dashboard UI was stale after a service change (cached plugin JS). Make plugin JS URLs cache-busted
   (version or mtime query) or served with no-cache headers.
4. MCP dashboard tools can go stale after an 8081 restart. Find the MCP server (`grep -rn "campaign_go" --include=*.py`)
   and make it reconnect per call or report a clear "8081 restarted, retry" error.
5. No GET exposes position, RC link/switches, battery voltage, stream freshness together.
6. Two 8081 instances once ran at the same time. Add a single-instance guard (port bind check or lock/pid file) at
   service start with a clear message.
7. Pack/voltage gates and the cooldown/resting_v steps in the runner: check each failure produces a clear
   `reason` the agent can read in one `campaign_state` call.

## Changes
A. **One preflight call.** `GET /api/campaign/preflight` returns `{ok, checks:[{name, value, pass, fix}]}` for:
   service up (single instance), link + stream fresh (age, dropped), firmware identity matches the axf on disk,
   g_wfb_status fresh, RC link present, arm_state disarmed (with the raw source field), position near origin,
   battery voltage, runner idle, log plan loadable. Add an MCP tool `campaign_preflight` that returns it.
   Reuse `check_live_ready`/`streams.preflight_check`; do not duplicate logic.
B. **One launch command.** `python -m ground_station.service.campaign_launch <campaign-name-or-yaml> --pack <id>
   [--rate N]`: validates (`load_campaign`), writes `logs/campaigns/launch/<campaign>_<YYYYmmdd-HHMM>.yaml`, prints
   the log plan table and the path. Exit non-zero with one clear line on any error.
C. **Panel UX** (`campaign-panel.js`): a top status banner (idle / waiting for go / flying flight n/m / paused:
   reason / done: outputs path), the preflight table (refresh button, red rows show `fix`), campaign + pack pickers
   (dropdown from a GET listing of saved/launch campaigns), the checklist, Go, and big Pause/Land/Abort.
   Keep the harness (`ground_station/service/tests/campaign_panel_harness.js`) passing and extend it for the new UI.
D. **Skill** `.claude/skills/workflow-b/SKILL.md` (tracked; stage with `git add -f`): rewrite to the minimal path:
   Q1 campaign -> Q2 pack -> run `campaign_launch` (one command) -> Q3 log plan approve -> `campaign_preflight`
   (one MCP call; any red row = tell the operator its `fix`, stop) -> Q4 checklist -> "arm by RC, say go" ->
   `campaign_go` -> `campaign_state` once per flight -> send outputs. Update `test_workflow_b_skill.py`.
E. **Failure-mode table** `docs/workflow-b/failure-modes.md`: every failure you found (the 7 above plus any
   other from reading `campaign_runner.py`, `campaign_live.py`, `campaign_api.py`, `abort_monitor.py`):
   symptom -> how the agent detects it (which field) -> what the agent does -> test that covers it.
F. **Review**: read `git log --oneline -40 -- ground_station/service` and list in the report any earlier
   workflow-B code that looks wrong; fix what is in scope.
