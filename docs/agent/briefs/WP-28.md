## Why
The operator wants the PID gains tuned **while the drone is flying**, not one candidate per flight. The existing
`ground_station/analysis/tuner.py` is a (1+1)-ES that tries one candidate per flight, which is too slow. Target: one hover flight evaluates
many candidates. The ground station switches the gains live every few seconds, excites each candidate briefly, scores it from
telemetry, and CMA-ES (Hansen) proposes the next generation. Warm start comes from the WP-26 FRF gains when available,
otherwise from the firmware defaults (`API/pid.c:23-24`).

## Design (numbers are PROPOSED; check each against the code and logs, and say so in the report)
- **Search space**: rate loop, with roll and pitch sharing one set: (Kp, Ki, Kd) in log space, within a trust region of +/-30% of the baseline.
  Yaw and the angle loop come later through config. Write gains through the existing knobs (`ground_station/analysis/controller_descriptor.py:43`,
  the `pid.yaml` descriptor, and the write path of `campaign_api.apply_params`).
- **Optimizer**: a dependency-free CMA-ES in numpy (pycma is not installed; do not add a dependency). Use lambda = 4 + floor(3 ln n),
  mirrored sampling, bound handling by repair, and seed it so it is deterministic.
- **One evaluation window** (about 4-6 s): write the candidate -> settle -> excite -> score. Excitation: a short CMD 0x14
  multisine or doublet on the rate loop (`TASK/send_data.c:1833-1870`). **Warning: CMD 0x14 idx 6 start resets the OF origin
  and the loc PID setpoints**, so either start each window from a hold at the origin, or find or propose a lighter excitation
  path (for example a rate doublet that does not reset the origin) and say which one you chose and why.
- **Cost J**: rate-tracking error (ITAE or RMS) + w*control effort/motor saturation + an oscillation penalty (spectral peak
  above f_c), computed from the logged frames for that window only. Give the formula and the weights in the docs.
- **Safety supervisor** (this matters most): if a window shows |angle| > limit, a rate-error spike, saturation, or fence proximity,
  revert to the baseline gains at once, mark the candidate infeasible, and shrink sigma. If a window has no telemetry or the link is lost,
  revert. Battery or time budget ends the run with the best-so-far gains **not** applied. The operator applies them
  through a verify flight. At most N consecutive failures stop the tuner. RC takeover always wins.
- **Gain lease (firmware question)**: if the link drops while a bad candidate is active, the gains stay in place. Check whether the
  firmware has a way to revert the gains on link loss. If it does not, design a minimal "gain lease" (the baseline is stored and
  restored if it is not renewed within T s, default OFF) and implement it only if it fits in about 40 lines in `API/pid.c` or
  `TASK/send_data.c` with a `*_ROW` style tunable. The CEO build-checks it. Otherwise, specify it in the report.
- **Scenario step `livetune`**: `livetune: {loop, axes, budget_s, max_evals, trust, sigma0}`. It holds hover while the tuner loop runs,
  using an additive change to `scenario_schema.py` and the runner. WP-26 adds an `excite` step at the same time, so keep the diff small. A
  campaign `ground_station/service/campaigns/livetune_rate_rp.yaml`: takeoff -> hold -> livetune -> hold -> land, with MRAC
  injection off through its knob.
