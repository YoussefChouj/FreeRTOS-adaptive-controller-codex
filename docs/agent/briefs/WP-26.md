## Why
The operator wants automatic PID tuning they can fly tomorrow through workflow B. The method was decided in WP-25. Read
`docs/agent/research/WP-25.md` first; it is the spec. In summary: excite the rate loop with the existing sysid
multisine/chirp, estimate the closed-loop FRF with the instrumental-variable estimator G = Phi_xd/Phi_ud, fit
integrator + lag + delay (reuse `ground_station/research/sim/cascade.py:432 fit_rate_plant` or its math), compute
rate-loop PID gains against margin specs, then verify in flight with auto-revert. Tune the rate loop first, then the angle loop.
During tuning flights, MRAC injection is off (`output_injection_on = 0`).

## What already exists (verify with Grep, then Read using offset/limit)

  idx 6 is start/abort; idx 7 is geofence. **Starting a run (idx 6) resets the optical-flow origin and the loc PID setpoints to (0,0).**
  That is safe only if the drone is holding at the origin when the step starts. Handle this: the step must start from a hold at the
  scenario origin, and the report must flag the risk.

## Changes
A. **Identification + gain module**: `ground_station/autotune/` with
   - `frf.py`: IV FRF estimation from a logged ID run (Welch cross-spectra, coherence), plus `fit` (integrator + first-order
     lag + delay, which may wrap `fit_rate_plant`).
   - `design.py`: rate-loop PID design for a target crossover / phase margin / gain margin. Output both continuous gains and
     firmware gains, clamp the change to at most a PROPOSED +/-30% of current per step, and refuse to design when coherence
     is low or the fit is poor (the reason must be a string).
   - `cli.py`: `python -m ground_station.autotune.cli <session-or-csv> --axis roll|pitch|yaw [--loop rate|angle]`. It prints
     the FRF fit, margins, the proposed gains, and the exact knob symbols and values, and writes a JSON proposal next to the log.
   Tests use synthetic data (a known plant + noise means the fit recovers the parameters, low coherence is refused, the clamp holds, the
   firmware conversion is right).
B. **Campaign step `excite`** (additive change to `scenario_schema.py` and the runner, kept minimal because WP-23 edits the
   service in parallel): `excite: {axis, signal, f0, f1, amp, duration_s}` sends CMD 0x14 idx 0-5 then 6, holds for `duration_s`,
   then aborts or waits for SysID_IDLE. It only runs when the previous step is a `hold` at the origin. Add the fake-drone support
   and tests. Make sure the 0x03 frame is in the step's log plan.
C. **Campaigns** under `ground_station/service/campaigns/`:
   - `autotune_rate_roll.yaml` and `autotune_rate_pitch.yaml`, each: takeoff -> hold -> excite (multisine) -> hold -> land, with
     MRAC injection set to 0 through its knob.
   - `autotune_verify.yaml`: apply the proposed gains -> hover + doublet -> land, then compare against `G_prev`; revert if it is worse.
   Amplitudes and frequency bands come from WP-25, marked PROPOSED. Every flight stays inside the soft fence
   (z <= 1.4, |x| <= 1.3, |y| <= 1.7).
D. **Docs**: `docs/workflow-b/autotune.md` (<= 80 lines) gives the operator flow: which campaign, how many packs, what the
   agent runs between flights (the cli), the pass/fail and revert rule, and the abort conditions.
