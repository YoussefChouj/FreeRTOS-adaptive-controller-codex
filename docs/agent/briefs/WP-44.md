## Why
The operator tunes in Keil by writing RAM over SWD: pick `traj_id`, edit `traj_p.*`, write `traj_go = 1`. WiFi has no
generic write today (only the fixed command table), so ground code must upload whole programs (CMD 0x1C, ~60 s). This WP adds
one WiFi command that writes ONE allowlisted variable by name, live, in flight, with the existing ACK/applied reply.

## Scope
1. Firmware: one new GS command (pick a free id in the `send_data.c` table; document it) "VAR_WRITE".
   Payload: `uint32 name_crc` (CRC-32 of the variable name string exactly as written in the row, zlib/IEEE polynomial, so
   ground uses `zlib.crc32`) + the value (float32 for float rows, integer for integer rows; you define the exact layout).
2. Firmware allowlist as an aligned `VAR_WRITE_ROW(name, lvalue, type, min, max)` table, pid.c / `*_ROW` style. Rows, with
   min/max taken from the existing comments next to each variable (do not invent ranges; if a comment gives none, use the
   variable's legal enum/bool range and say so in the report):
   `traj_id`, `traj_go`, `traj_stop`, `traj_fence_off`, every `traj_p.*` field, `kp_id`, `kp_go` (TASK/StabilizerTask.c ~145),
   `vp_user_go` (~1509), `g_traj_ff_preset` (~1805). Unknown crc -> reject; out of range -> reject; reply with a distinct
   reject code per reason through the existing reply path. Never write anything not in the table.
3. Do not change `AutoflyTask_PathArbitrate` or any existing command's behaviour (byte-for-byte outside the new code).
4. Ground: `WfbCommands.var_write(name, value)` (or a small sibling module) that reads the row table by parsing the
   `VAR_WRITE_ROW` lines from the C source (single source of truth, no copied list), checks name and range locally, sends,
   returns the outcome. Unit tests: frame bytes for one float row and one integer row, crc matches `zlib.crc32`, unknown name
   and out-of-range refused locally, and a test that every C row parses.
