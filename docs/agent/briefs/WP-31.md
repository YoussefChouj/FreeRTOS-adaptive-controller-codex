# WP-31 brief (CEO -> CTE), 2026-10-04. Firmware-in-the-loop simulator (SIL) and scenario matrix.

Base: `main`. No manager or workers: you, the CTE, write the code. Ignore the "manager report" part of CTE rule step 1.
Forbidden: Keil build, flash, the running 8081 service, motors, serial ports, `OBJ/`, `USER/`, `docs/flights/ledger.csv`,
`.agent-ops/manager.sh`, `.agent-ops/served/*`. Firmware `.c`/`.h` are read-only in this package.

## Why
Mature autopilots (PX4/ArduPilot SITL) run the real flight code against a plant model before any flight. We have the pieces, not the pipeline:
- measured physical parameters: `ground_station/research/sim/constants.py` (per-axis K, pole, delay; mass; arm; MOTOR_TAU; mixer gains);
- a calibrated plant and bench: `sim/bench/plant.py`, `sim/bench/calib_*.py`, `sim/bench/bench.py`, controllers `sim/bench/ctrl_*.py`, `sim/bench/fwpid.py`;
- host builds of firmware C: `API/tests/run_mrac_equiv.py`, `API/tests/test_mrac_equiv.c`, stubs in `API/tests/stubs*`;
- the cascade sim and plant fit: `ground_station/research/sim/cascade.py`.
Goal: one simulator that steps the REAL firmware controller code against a plant built from the measured parameters, and a
scenario matrix that runs every controller through independent and combined disturbances, so flights only test what passed in sim.

## Changes
A. `sim/sil/` (new): host-build `API/pid.c`, `API/mrac.c` (with the WP-27 variants of `API/mrac_variant.h`) and the mixer/clamp
   logic of `API/controller.c` where it can be stubbed, as a shared library (reuse the run_mrac_equiv flags and stubs; ctypes), stepped
   at the firmware dt (`API/pid.c`). Set tunables through the same index maps as CMD 0x01 and CMD 0x1D, so a sim preset equals a flight
   preset. If a file cannot be host-built, say which and why, and use the matching `sim/bench` python controller for it only, labelled
   "python, not firmware".
B. Plant from `constants.py` + `sim/bench/plant.py`: motor lag, per-axis transport delay, the firmware motor clamp and PWM range, sensor
   noise and estimator delay. Cite the source of every number; numbers you choose are PROPOSED.
C. Scenarios (composable dataclasses): hover 40 s at 0.8 m; doublet +/-0.4 m; dense figure-8 1.0 x 0.5 m at 0.3 m/s, 2 laps; step and gusting
   indoor wind; ground effect below 0.3 m; CoG offset; 100 g offset payload; swinging payload (pendulum); mass +/-15%; one motor at 80%;
   extra delay +5/+10 ms; battery sag (thrust gain drift over 90 s); sensor noise x2. Combined: all pairs of {wind, CoG offset, swinging
   payload, motor 80%, delay +10 ms} on the figure-8, plus one "worst plausible" stack.
D. Controllers: firmware PID default; PID designed by `ground_station/autotune` on the sim FRF; MRAC baseline; V1 refmodel (gamma x0.25 and x1);
   V2 sataware; PR (kappa_pr, crm_ell); 3L; V3 RBF12 (`-DMRAC_VARIANT=1` build). Presets from `ground_station/analysis/controllers/mrac_v*.yaml`.
E. Metrics with the flight abort rules of `docs/analysis/controller-roadmap-2026-10-03.md:176-198`: position RMSE, max tilt, time at motor
   clamp, |u_ad|/|u_nom|, Theta-norm growth, abort-rule hits. Host time per step is not STM32 cost: say so. Write
   `docs/analysis/sil-matrix-2026-10-04.md` (<= 150 lines): a table per scenario group, and per controller "fly / fly with limits / do not fly" + reason.
F. Validation: replay at least one logged hover and one logged doublet (`logs/sessions/`, `logs/campaigns/`) through the SIL with the logged
   commands; report sim-vs-log error. If no usable log exists, say the matrix is unvalidated.
G. CLI: `python -m sim.sil.run --controller <name> --scenario <a>[+<b>...]` and `--matrix`. Deterministic for a seed.
