adaptive-controller variants. This package decides WHAT to implement, from evidence, so the next package (WP-27)

Q1. **Reference model order.** We have flight logs with MRAC in active and shadow mode. Find them
    (`logs/sessions/`, `logs/campaigns/`, `docs/flights/`, grep the recorder var names used by `API/mrac.c`).

    and any sign of the reference model being faster than the plant. Recommend one, with numbers you measured.
    If the logs lack the signals needed, say exactly which vars are missing and add them to a proposed log plan.
Q2. **Performance recovery** for dense trajectory following. Is it implemented in firmware (`API/mrac*.c/h`,
    `API/mrac_variant.h`, `API/controller.c`)? In sim (`sim/bench/ctrl_p2_yucelen.py`, `.agent-ops/tasks-src/p2-c1-yucelen.md`,

Q3. **3-layer architecture** (the operator's idea): `.agent-ops/tasks-src/night-w3-mrac3l.md` (layer 1 physics basis,

    (`.agent-ops/out/night/REPORT.md`). State what worked in sim, the CPU/RAM cost on the STM32F4 at the rate loop,
    and a firmware design.
Q4. **Structured vs unstructured variants** for unsymmetric/dynamic loads (CoG offset, swinging or shifting payload),
    dense trajectories and indoor wind/ground effect: which regressor features (structured) and which unstructured
    approximator (RBF/neural, low-frequency learning, concurrent learning, L1-style filter) the sim bench and the
