# Today, step by step: tilted figure-8 with nose-follows-path, PID vs vp15-vp24, three loads

**Bottom line.** Start by flashing; the new code is built but not yet on the drone. Then do one nose check, then fly the
matrix: one figure-8 per takeoff, PID first, then the vp rows. The auto-land gate is on by default.
Every number marked PROPOSED comes from replay or computation. None of it has flown yet.

Think of it as a driving test on a fixed course. The figure-8 is the course and each controller is a driver. The load
is a heavy bag on one seat. With the nose following the path, the course uses every axis (x, y, z, roll, pitch, yaw),
so every driver is scored on the same corners.

## 2. The auto-land gate (on by default)

| situation | what to do |
|---|---|
| turn the gate off completely | `g_land_gate_enable = 0` |
| keep only the low-voltage check | `g_land_gate_enable = 1` |
| keep only the motor-pin check | `g_land_gate_enable = 2` |
| after an auto-landing, why? | `g_land_gate_trip`: 1 low voltage, 2 motor pinned. It clears on the next takeoff |

The gate fires at most once per flight. It sets the landing phase and stops any running trajectory.
`g_land_gate_trip` is **not** in the VOFA presets, so read it in the Keil watch after each landing.

Charge every pack to 16.8 V. The gate trips at 14.3 V under load, so a half-charged pack ends the flight early.

## 3. Per-flight settings (on the ground)

1. **`kp_id = 5`**, then pulse `kp_go = 1`, then confirm `kp_active == 5`. Row 5 turns optical-flow channel 1 off.
   It keeps channel 2 and the IMU prediction, runs MRAC on all four axes (mask 0x0F) at full learning rate,
   and adds z headroom (`TASK/StabilizerTask.c` KP table). `kp_id` takes effect only on the ground, so set it before
   arming.
   **Trade-off (replay vs 10-07 video truth, measured 2026-10-10):** position error rms is 22 / 21 cm with channel 1
   on and 32 / 45 cm with it off (roam / step B). The "gyro leak" reason for dropping channel 1 did not hold:
   de-rotating the flow with the gyro made velocity worse against truth (the module already compensates). The one
   remaining reason for row 5 is the bench load-swing result (swing about 16° with channel 1 off vs 22-29° on). For
   runs without a hanging load, use **row 7** instead (row 5 with channel 1 on, same z headroom). Pick one row for
   the whole matrix so presets stay comparable.
2. Select the controller row the same way as yesterday (`docs/lab/today-2026-10-09-arm.md`).
   For PID, switch ch8 to off.
3. Run one trajectory per takeoff. Land, change the setting, take off again.

## 5. The run matrix

The path is a Gerono figure-8, `f8_a_cm = 70`, `move_s = 20`, `ramp_s = 2`, with `f8_tilt_deg = 30`.
At tilt 30 the path spans y ±61 cm and z ±35 cm. **Hover at 0.75-1.05 m before `traj_go`**, or it is refused with
`0xEF` (the 0.4 m floor). Speed ladder (computed):

| `f8_laps` | peak speed | peak yaw rate, flat / tilt 30 |
|---|---|---|
| 1 | 35 cm/s | 64 / 71 °/s |
| 1.5 | 52 cm/s | 95 / 107 °/s |
| 2 | 69 cm/s | 127 / 143 °/s |

Above the yaw cap the yaw lags the path. The cap is the smaller of `traj_p.yaw_rate_dps` (default 90) and the
limit mode's yaw cap (below). The old image clamped yaw rate at 60 °/s, below the 90 it was asked for. That was a bug,
and mode 0 now uses 90. Every controller gets the same lag, so the comparison stays fair. For mode 1 or 2, also raise
`traj_p.yaw_rate_dps` to 120 or 160.

**Speed feed-forward (new, PROPOSED, not flown).** Until now the preset figure-8 sent only a moving position, and
the position loop (Kp 0.8) chases it from behind, like a dog on a lead. Model check (Kp 0.8 and Kd 4.0 from
`API/pid.c`, velocity loop taken as first-order with 0.2-0.4 s lag, computed 2026-10-10): the tracking error is
24-25 cm rms at laps 1 and 38-42 cm at laps 2 without feed-forward, and 3-6 cm and 7-15 cm with it. So the old
figure-8 flew noticeably smaller and later than planned. Now the trajectory also sends its x, y, z and yaw rates
(`g_traj_vff_x/y/z/yaw`), which are added to the velocity, climb-rate and yaw-rate loops within the mode's caps.
`g_traj_ff_preset = 0` restores the old behaviour. It is the same for every controller, so the matrix stays fair, but
do not compare today's figure-8 errors with older flights.

### Limit modes (`lim_mode`, set on the ground; `lim_active` shows the applied mode)

| `lim_mode` | lean cap | xy velocity cap | fastest trajectory | yaw rate cap | use |
|---|---|---|---|---|---|
| 0 slow (boot default) | 15° | 120 cm/s | 80 cm/s | 90 °/s | the matrix above |
| 1 conservative | 20° | 150 cm/s | 110 cm/s (`f8_laps` 3 = 104 cm/s fits) | 120 °/s | faster laps, still gentle |
| 2 max | 30° | 200 cm/s | 150 cm/s | 160 °/s | limit testing, PID first, no load |

The caps in mode 2 sit just under limits that are fixed in `API/pid.c`: the velocity loop's output of 600 cm/s²
(31.4° lean) and the yaw angle loop's 160 °/s. To go past them, those limits would have to change too.
Measured hover throttle on 10-07 was 0.43-0.47 (motor command, not 0.23 as the old notes said). At a 30° lean,
the drone needs about 0.55 collective (computed), which leaves room. Z limits do not change with the mode: 1 m/s,
±40 cm, and the 0.4 m floor. A trajectory faster than the mode allows is refused with `0xEE`. The mode applies only
when it changes, so a dashboard write to the lean cap afterwards still holds. Fly modes 1 and 2 after the matrix.
