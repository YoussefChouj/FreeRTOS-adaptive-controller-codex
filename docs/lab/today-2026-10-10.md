# Today, step by step: tilted figure-8 with nose-follows-path, PID vs vp15-vp24, three loads

**Bottom line.** Start by flashing; the new code is built but not yet on the drone. Then do one nose check, then fly the
matrix: one figure-8 per takeoff, PID first, then the vp rows. The auto-land gate is on by default.
Every number marked PROPOSED comes from replay or computation. None of it has flown yet.

Think of it as a driving test on a fixed course. The figure-8 is the course and each controller is a driver. The load
is a heavy bag on one seat. With the nose following the path, the course uses every axis (x, y, z, roll, pitch, yaw),
so every driver is scored on the same corners.

## 1. Flash (first thing, before any flight)

Close the dashboard (8081), VOFA Studio, VOFA+, any stream_log terminal and the Keil debug session.
Plug in the ST-Link and the radio (COM6), power the drone, then run:

```bash
python -m ground_station.flashtool.rebuild_and_flash --yes
```

The run must exit with code 0. On any non-zero code, stop and paste the output. Never add `--force`.
The codes: 2 means UV4 is still open, 3 means the build failed, 5 means the target or COM6 is dark.

In the Keil watch, check that these values read back on the new image:

| variable | expect |
|---|---|
| `g_land_gate_enable` | 3 (low-V + motor-pin both on) |
| `g_land_gate_trip` | 0 |
| `traj_p.yaw_follow`, `traj_p.yaw_rate_dps`, `traj_p.yaw_nose_deg` | 1, 90, 90 |
| `traj_p.f8_tilt_deg` | 0 (set it per run, below) |
| `waypoint_spacing` | 0 (continuous reference; the old image had 5 cm steps). On an old image, set it to 0 by hand |

If these are missing, you are still on the old image. Do not fly the tilted figure-8 on it.

## 2. The auto-land gate (on by default)

| situation | what to do |
|---|---|
| turn the gate off completely | `g_land_gate_enable = 0` |
| keep only the low-voltage check | `g_land_gate_enable = 1` |
| keep only the motor-pin check | `g_land_gate_enable = 2` |
| after an auto-landing, why? | `g_land_gate_trip`: 1 low voltage, 2 motor pinned. It clears on the next takeoff |

The gate fires at most once per flight. It sets the landing phase and stops any running trajectory.
`g_land_gate_trip` is **not** in the VOFA presets, so read it in the Keil watch after each landing.

Charge every pack to 16.8 V. The gate trips at 14.3 V under load, so a half-charged pack ends the flight early.

## 3. Per-flight settings (on the ground)

1. **`kp_id = 5`**, then pulse `kp_go = 1`, then confirm `kp_active == 5`. Row 5 turns optical-flow channel 1 off.
   It keeps channel 2 and the IMU prediction, runs MRAC on all four axes (mask 0x0F) at full learning rate,
   and adds z headroom (`TASK/StabilizerTask.c` KP table). `kp_id` takes effect only on the ground, so set it before
   arming.
2. Select the controller row the same way as yesterday (`docs/lab/today-2026-10-09-arm.md`).
   For PID, switch ch8 to off.
3. Run one trajectory per takeoff. Land, change the setting, take off again.

## 4. Nose check (first figure-8 of the day; PID, no load)

## 5. The run matrix

The path is a Gerono figure-8, `f8_a_cm = 70`, `move_s = 20`, `ramp_s = 2`, with `f8_tilt_deg = 30`.
At tilt 30 the path spans y ±61 cm and z ±35 cm. **Hover at 0.75-1.05 m before `traj_go`**, or it is refused with
`0xEF` (the 0.4 m floor). Speed ladder (computed):

| `f8_laps` | peak speed | peak yaw rate, flat / tilt 30 |
|---|---|---|
| 1 | 35 cm/s | 64 / 71 °/s |
| 1.5 | 52 cm/s | 95 / 107 °/s |
| 2 | 69 cm/s | 127 / 143 °/s |

Above 90 °/s the yaw lags the path, because the yaw command is capped at `yaw_rate_dps` 90. Every controller gets the
same lag, so the comparison stays fair.

| block | load | controllers | laps | name the log |
|---|---|---|---|---|
| A | none | PID, then vp15-vp24 | 1, then 1.5 | `vpNN_none_l1` |
| B | 0.3 kg on one arm | PID, then vp15-vp24 | 1, then 1.5 | `vpNN_arm300_l1` |
| C | 0.2 kg under one motor | PID, then vp15-vp24 | 1, then 1.5 | `vpNN_mot200_l1` |
| D (optional) | best two of B/C | best two + PID | 2 | `vpNN_<load>_l2` |

Skip 0.45 kg on the arm; the prep review judged it infeasible. If the batteries run short, cut vp rows, never PID.
PID is the baseline for every row.

Recording: use one VOFA Studio preset per flight, `vpNN` for the row you fly. Studio runs only one preset at a time.
Studio and the dashboard both use UDP 14550, so only one of them can run.

## 6. Video ground truth (phone)

Today's setup is the same as `ground_station/analysis/video_truth.py`. Put the phone on a tripod that does not move,
put the floor marks or the ChArUco board in view, and keep the 4 orange guards visible. Start the video before you
arm and stop it after you disarm. The script finds the time offset from horizontal speed. Height comes from
telemetry, not from the video.

Cheap things for today that make the truth better (hardware only, no code):

| do this | why |
|---|---|
| tape the 3 numbers: QR black-square edge, lens height, lens-to-pad distance | settles the scale question in the 10-07 research doc |
| a sharp visible event at the start (phone torch flash, or a hand clap in frame) | a second sync check next to the speed correlation |
| swap **one** guard for white (blue or green resists glare better); write down which motor | breaks the 4-fold symmetry, so the video can later solve yaw and full 6-DoF pose (`docs/agent/video-truth-review-2026-10-10.md`). Keep white things out of the background |
| tape the guard-to-guard spacing (centre to centre) | PnP needs it to get height from the video |
| lock the phone's exposure and focus, 60 fps if it can | less blur in the fast lobes |

Pipeline improvements, PROPOSED and not built:
Full ranked list in `docs/agent/video-truth-review-2026-10-10.md`. The top items:
1. **6-DoF pose from the 4 guards** (PnP, IPPE), using the odd guard: x, y, z, roll, pitch, yaw from one phone,
   with no telemetry height.
2. **Audio-onset sync** (motor spool-up) next to the speed correlation.
3. **RTS smoother** on the video track, which also gives truth velocity.
4. **`evo` ATE/RPE** metrics.
5. A second phone only if PnP depth is too noisy.

The overlay (`video_truth overlay`) already draws the planned path, the drone's own estimate and the video truth
on the video. That is the clip for the professor.
