**Bottom line.** Start by flashing; the new code is built but not yet on the drone. Then do one nose check, then fly the
matrix: one figure-8 per takeoff, PID first, then the vp rows. The auto-land gate is on by default.
Every number marked PROPOSED comes from replay or computation. None of it has flown yet.

Think of it as a driving test on a fixed course. The figure-8 is the course and each controller is a driver. The load
is a heavy bag on one seat. With the nose following the path, the course uses every axis (x, y, z, roll, pitch, yaw),
so every driver is scored on the same corners.

## 2. The auto-land gate (on by default)

| situation | what to do |
|---|---|
| turn the gate off completely | `g_land_gate_enable = 0` |
| keep only the low-voltage check | `g_land_gate_enable = 1` |
| low voltage lands, motor pins are not counted | `g_land_gate_enable = 1` |
| after an auto-landing, why? | `g_land_gate_trip`: 1 low voltage. It clears on the next takeoff |
| did a motor pin? | `g_land_gate_sat_n` (runs ≥ 0.35 s this flight), `g_land_gate_sat_max_s` (longest run). Cleared at takeoff, kept after landing |

Only low voltage lands. The gate fires at most once per flight; it sets the landing phase and stops any running
trajectory. A pinned motor never lands (one unloaded flight left only 109 ms of margin, so loads and mode 2 would
false-trip). The trip flag and both pin counters are in the vp15-vp24 and `pid_flight_test` presets (25 / 10 Hz).

Charge every pack to 16.8 V. The gate trips at 14.3 V under load, so a half-charged pack ends the flight early.

## 5. The run matrix

The path is a Gerono figure-8, `f8_a_cm = 70`, `move_s = 20`, `ramp_s = 2`, with `f8_tilt_deg = 30`.
At tilt 30 the path spans y ±61 cm and z ±35 cm.

**Fixed start point (new, built 2026-10-10, not flown).** On `traj_go` the drone first flies from wherever it
hovers to `(start_x_cm, start_y_cm, start_z_m)` = (0, 0, 0.85 m). That takes at least `goto_s` = 4 s, longer if the
limit mode's speed needs it. It then hovers there for `settle_s` = 2 s while the nose turns to the path's first
heading, and starts the figure-8. So every run starts at the same place and heading. `traj_phase` reads 4 (flying
there) and 5 (settling) before 1 (move). `traj_stop` during 4 or 5 finishes the flight there, holds, and ends with
status 4. The return leg comes back to (0, 0, 0.85). `traj_p.start_fixed = 0` restores the old behaviour (the
preset runs around the hover point). The goto and settle are not counted in the 25 s cap (move + return + hold),
so a run is about 6 s longer in the air. Speed ladder (computed):

| `f8_laps` | peak speed | peak yaw rate, flat / tilt 30 |
|---|---|---|
| 1 | 35 cm/s | 64 / 71 °/s |
| 1.5 | 52 cm/s | 95 / 107 °/s |
| 2 | 69 cm/s | 127 / 143 °/s |

Above the yaw cap the yaw lags the path. The cap is the smaller of `traj_p.yaw_rate_dps` (default 90) and the
limit mode's yaw cap (below). The old image clamped yaw rate at 60 °/s, below the 90 it was asked for. That was a bug,
and mode 0 now uses 90. Every controller gets the same lag, so the comparison stays fair. For mode 1 or 2, also raise
`traj_p.yaw_rate_dps` to 120 or 160.

**Speed feed-forward (new, PROPOSED, not flown).** Until now the preset figure-8 sent only a moving position, and
the position loop (Kp 0.8) chases it from behind, like a dog on a lead. Model check (Kp 0.8 and Kd 4.0 from
`API/pid.c`, velocity loop taken as first-order with 0.2-0.4 s lag, computed 2026-10-10): the tracking error is
24-25 cm rms at laps 1 and 38-42 cm at laps 2 without feed-forward, and 3-6 cm and 7-15 cm with it. So the old
figure-8 flew noticeably smaller and later than planned. Now the trajectory also sends its x, y, z and yaw rates
(`g_traj_vff_x/y/z/yaw`), which are added to the velocity, climb-rate and yaw-rate loops within the mode's caps.
`g_traj_ff_preset = 0` restores the old behaviour. It is the same for every controller, so the matrix stays fair, but
do not compare today's figure-8 errors with older flights.

### Limit modes (`lim_mode`, set on the ground; `lim_active` shows the applied mode)

| `lim_mode` | lean cap | xy velocity cap | fastest trajectory | yaw rate cap | use |
|---|---|---|---|---|---|
| 0 slow (boot default) | 15° | 120 cm/s | 80 cm/s | 90 °/s | stages 1, 4, 5 |
| 1 conservative | 20° | 150 cm/s | 110 cm/s (`f8_laps` 3 = 104 cm/s fits) | 120 °/s | faster laps, still gentle |
| 2 max | 30° | 200 cm/s | 150 cm/s | 160 °/s | limit testing, PID first, no load |

The caps in mode 2 sit just under limits that are fixed in `API/pid.c`: the velocity loop's output of 600 cm/s²
(31.4° lean) and the yaw angle loop's 160 °/s. To go past them, those limits would have to change too.
Measured hover throttle on 10-07 was 0.43-0.47 (motor command, not 0.23 as the old notes said). At a 30° lean,
the drone needs about 0.55 collective (computed), which leaves room. Z limits do not change with the mode: 1 m/s,
±40 cm, and the 0.4 m floor. A trajectory faster than the mode allows is refused with `0xEE`. The mode applies only
when it changes, so a dashboard write to the lean cap afterwards still holds. Modes 1 and 2 are stages 2 and 3 of the matrix below.

## 6. Video ground truth (phone)

Record every flight, but the analysis runs after the campaign (it takes too long at the lab). It gives the truth
path flown vs the preset, and the data to tune the estimator.

Today's setup is the same as `ground_station/analysis/video_truth.py`. Put the phone on a tripod that does not move,
put the floor marks or the ChArUco board in view, and keep the 4 orange guards visible. Start the video before you
arm and stop it after you disarm. The script finds the time offset from horizontal speed. Height comes from
telemetry, not from the video.

Cheap things for today that make the truth better (hardware only, no code):

| do this | why |
|---|---|
| tape the 3 numbers: QR black-square edge, lens height, lens-to-pad distance | settles the scale question in the 10-07 research doc |
| a sharp visible event at the start (phone torch flash, or a hand clap in frame) | a second sync check next to the speed correlation |
| swap **one** guard for white (blue or green resists glare better); write down which motor | breaks the 4-fold symmetry, so the video can later solve yaw and full 6-DoF pose (`docs/agent/video-truth-review-2026-10-10.md`). Keep white things out of the background |
| tape the guard-to-guard spacing (centre to centre) | PnP needs it to get height from the video |
| lock the phone's exposure and focus, 60 fps if it can | less blur in the fast lobes |
| write down the odd guard's motor **and its body angle** (nose = 0°, CCW positive, e.g. front-left = 45°) | `--odd-deg` for the pose solver; a wrong arm turns yaw by 90° |
| mount the phone **high, looking down at least 30°** | the 4 guards are one plane; seen edge-on, the pose has two near-equal answers |
| keep the room **bright** | dim light makes phones drop frames (variable frame rate); the report flags it |
| keep the whole figure-8 in the **middle band** of the frame, not the top or bottom edge | the phone reads rows over 15-30 ms (rolling shutter), so frame edges are captured at different times |
| keep the phone recording from **before arm** | the audio sync listens for the motors spooling up |

Pipeline (built 2026-10-10, tested on synthetic data only; details and web sources in
`docs/agent/video-truth-review-2026-10-10.md`):

```
python -m ground_station.analysis.video_truth run VIDEO --cam CALIB.json --marks MARKS.json --csv SESSION.csv --out RUN_DIR --sync audio
python -m ground_station.analysis.guard_pose pose VIDEO --cam CALIB.json --marks MARKS.json --csv SESSION.csv --run RUN_DIR --spacing B_m --odd-deg D --sync audio
python -m ground_station.analysis.guard_pose audio VIDEO --csv SESSION.csv
python -m ground_station.analysis.guard_pose sbs PID.mp4 T0 VP.mp4 T0 --out sbs.mp4 --labels PID,vp20
```

- `video_truth run --sync` takes `takeoff`, `speed`, `audio` or a number of seconds. Compare `audio` with `speed`; if
  they disagree by more than a frame or two, trust neither and look at the clip.
- `guard_pose pose` writes `pose.csv` (x, y, z, roll, pitch, yaw, truth velocity and 1σ), `truth.tum`, `est.tum` and
  `pose_report.json`: ATE/RPE, height bias, velocity rms vs the estimator, yaw vs `imu_data.yaw`, predicted depth σ,
  and `frame_dt_ms`. Options: `--guard-offset` (guard plane height above the drone's z point), `--stride`, `--static`.
- `video_truth overlay` now also draws the planned heading (yellow), the truth heading (green, needs `pose.csv`) and
  an error strip along the bottom. With `sbs`, that is the clip for the professor.
- `evo` (`evo_ape tum truth.tum est.tum -a`) is optional and not installed; `pose_report.json` already has ATE/RPE.
