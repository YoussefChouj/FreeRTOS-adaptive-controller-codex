# D3: how the xy MRAC breaks when it wraps ADRC, LQR or MPC instead of PID (2026-10-22)

Question (user, 10-22): on the flights with ADRC, LQR or MPC plus the adaptive layer, how can that setup break?
User's view: in a model reference adaptive controller the adaptation law should change with the nominal
controller, because it is wrapped around it.

Script: `tools/d3_mrac_wrap_sim.py`, run from the repo root: `PYTHONPATH=. python tools/d3_mrac_wrap_sim.py`.
All numbers below come from that run (one seed). The code finding is read from the firmware source.

## Bottom line

The user is right, and the firmware does the opposite today. For every xy controller kind the MRAC reference is
the **PID** position loop's velocity demand. ADRC, LQR and MPC ignore that demand and compute their own command,
so MRAC becomes a second controller that pulls the drone toward the PID's velocity profile. In sim, around ADRC
this doubles to triples the hold error and drives the command into saturation. Using the nominal controller's
own closed loop as the reference (a "nominal twin") removes the fight, as long as the adaptation gain is low.

Analogy: a driving instructor with a second brake pedal who was trained on one student's style. With that student
the pedal helps. With a different student, who brakes later on purpose, the instructor keeps braking against
them, and the car jerks.

## Code finding (firmware, read from source)

| step | where | what it does for kind != 0 (ADRC / LQR / MPC) |
|---|---|---|
| PID position loop | `TASK/StabilizerTask.c:2243-2247` | still runs: `locxsPID.Des` = PID velocity demand + vx |
| nominal command | `TASK/StabilizerTask.c:2256` | `XyCtrl_Step(...)` overwrites `locxsPID.U`; it uses position and velocity, **not** `locxsPID.Des` |
| MRAC reference input | `API/mrac.c:2025` | `r_x = locxsPID.Des * 0.01`: the PID demand, for every kind |
| MRAC u_nom | `TASK/StabilizerTask.c:2267`, `API/mrac.c:2035` | the full nominal command (ADRC / LQR / MPC output). The comments say "PID-only accel" and "PID only", which is wrong for kind != 0 |
| injection | `API/controller.c:105` | `u_ad * fade * inj_alpha` added to the nominal command |

So the reference model (first order, bandwidth 2, fitted on PID flights) tracks a signal the active controller
never follows. MRAC reads the gap between the PID's velocity plan and what ADRC actually does as a "plant error"
and adapts to cancel it.

## Evidence (sim, measured)

One axis at 100 Hz. Plant and ADRC from `API/xy_ctrl_gains.h` (same model as `test_xy_ctrl_adrc_noise`),
21-tick loop delay, 0.9 cm position noise, 2 cm/s velocity noise. MRAC reduced to the core of the xy velocity
layer: regressor [1, v, v tanh v, u_nom], output clipped to 1 m/s^2, e-modification, |W| <= 2. Two references:

- **firmware**: first-order model, bandwidth 2, driven by the PID velocity demand (what the drone does today);
- **twin**: the velocity of a noise-free copy of the same nominal controller on the header plant (the nominal
  closed loop, controller-agnostic).

Gamma (adaptation gain) 1 and 5 are swept; the firmware gamma was not read. Hold scenario: a 40 cm step, then a
40 cm/s^2 gust from 10 s (about 2.3 deg of lean). Scores from 3 s on.

| nominal | MRAC reference | gamma | rms err (cm) | max err (cm) | rms cmd (cm/s^2) | time saturated |
|---|---|---|---|---|---|---|
| PID | off | - | 12.09 | 21.5 | 105.3 | 1.1 % |
| PID | firmware | 1 | 6.38 | 21.0 | 116.2 | 2.7 % |
| PID | firmware | 5 | 5.23 | 20.7 | 139.4 | 5.9 % |
| PID | twin | 1 | 7.62 | 21.5 | 111.0 | 1.9 % |
| ADRC | off | - | **1.70** | 10.4 | 87.2 | 0.3 % |
| ADRC | firmware | 1 | 3.12 | 11.9 | 96.1 | 0.7 % |
| ADRC | firmware | 5 | **5.44** | 14.3 | 213.9 | **38.0 %** |
| ADRC | twin | 1 | **1.72** | 10.4 | 90.6 | 0.5 % |
| ADRC | twin | 5 | 3.85 | 10.5 | 174.1 | 21.9 % |

Same pattern on the other scenarios (rms error in cm):

| case | ADRC off | ADRC + firmware ref, gamma 1 / 5 | ADRC + twin ref, gamma 1 / 5 | PID off | PID + firmware ref, gamma 1 / 5 |
|---|---|---|---|---|---|
| plant gain x0.85 (model error) | 1.87 | 3.09 / 5.80 | 1.83 / 5.80 | 18.65 | 6.92 / 5.37 |
| 0.25 Hz sine + gust | 25.47 (*) | 25.78 / 26.98, saturated 24-32 % | 25.23 / 25.49, saturated 0.6 % at gamma 1 | 27.98 | 13.47 / 11.81 |

(*) The sim's ADRC port has no velocity feed-forward, so its sine error is a sim artefact. Compare only the
saturation on that row: the firmware reference pushes ADRC from 0.4 % to 24-32 % saturated time; the twin
reference at gamma 1 does not.

What the numbers say:

1. **Around PID the firmware reference is consistent and helps**: it halves the error in every case, more than the
   twin does, because it also adds authority to the PID velocity loop.
2. **Around ADRC the firmware reference fights the controller**: error x1.8 at gamma 1 and x3.2 at gamma 5, and
   the command saturates 38 % of the time.
3. **The twin reference is neutral to slightly better at gamma 1** (1.72 / 1.64 vs 1.70, model-error case 1.83 /
   1.78 vs 1.87) and adds no saturation.
4. **Gain must change too.** With the twin reference, gamma 5 still hurts ADRC (3.8-6.6 cm, 9-44 % saturated).
   ADRC already cancels disturbances with its extended state observer; u_ad and the observer's disturbance
   estimate are correlated +0.37 to +0.90 in every ADRC case, so the two estimators fight over the same signal
   through the 210 ms delay. A fast MRAC on top of a disturbance observer needs a lower gain (or a split in
   frequency: MRAC below the observer bandwidth).
5. **What the ADRC observer is fed** (the final command, as `XyCtrl_Commit` does today, or the nominal command
   only) made no consistent difference in this sim.

## Limits of this sim

- MRAC is reduced: no projection operator, no tanh output saturation, no hard freeze, no fade, no V1 delay
  compensation, no `crm_ell`. Its exact numbers are not the firmware's.
- Velocity noise 2 cm/s is assumed, not measured. One seed.
- LQR and MPC are not simulated. They also ignore `locxsPID.Des`, so the same mechanism is expected (inference).
- No flight log was used. The 10-21 adrc / lqr / mpc plus MRAC flights should be checked for the same signs:
  u_ad growing against the nominal command, and more time at the tilt cap than the same controller alone.

## Proposed fixes (firmware: operator decision, none applied)

| # | change | effect | risk |
|---|---|---|---|
| A (no build) | treat today's adrc / lqr / mpc plus MRAC flights as "MRAC around a mismatched reference" in the thesis analysis, and fly those A/Bs with MRAC injection off on the xy axes (learning on, injection off) | no wrong conclusion from a broken setup | none |
| B (firmware) | for kind != 0, drive `r_x` from a nominal twin: run `XyCtrl_Step` on the header plant (no noise, no u_ad) and use its velocity as the reference velocity | controller-agnostic reference; matches the thesis claim | one more `XyCtrl_Step` per axis per tick (CPU); needs a replay test that fails on the old code |
| C (firmware) | per-kind gamma row in the xy MRAC table (lower for ADRC, which already has a disturbance observer) | stops the two estimators fighting | needs a sim sweep per kind first |
| D (comment) | fix "PID-only accel" (`TASK/StabilizerTask.c:2265`) and "PID only" (`API/mrac.c:2035`) | the code says what it does | none |

Suggested order: A today, D with the next firmware change, B + C together with a sim sweep (LQR and MPC ported
into `tools/d3_mrac_wrap_sim.py`) before any flight.

## Standard this follows

Adaptive augmentation of a baseline controller (Lavretsky and Wise, *Robust and Adaptive Control*, 2013, the
chapters on augmenting a baseline linear controller): the reference model is the closed loop of the baseline
controller with the nominal plant, so the adaptive term is zero when the plant matches the model and acts only
on the mismatch. Cited from memory, so UNVERIFIED until checked against the book. The twin reference is that
rule applied to any baseline, which is what makes the MRAC layer controller-agnostic.
